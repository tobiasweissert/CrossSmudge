# Proposed Lua recoverable-download contract — API5, NOT enabled

Status: independently reviewable candidate, not an approved API or implemented Lua binding. Existing API3/public test release and frozen API4 remain unchanged. Record format remains RDS1 version 1; API version and record version are different. This file supersedes no published API4 atomicity promises: callers must opt into a separately advertised `download_recovery_v1` capability before using these proposed API5 operations. API4 callers must never be silently routed into weaker guarantees.

## Proposed operations and response types

- `smudge.http.download_recoverable(url, options)` starts one bounded asynchronous download. URL, domain, public-address, TLS, time, cancellation, body and application-path policies remain mandatory. Options cannot name physical slots/paths. One app-scoped store, two fixed numeric files, at most 2 MiB of payload per slot. No redirects or credential forwarding added by this contract.
- `smudge.http.poll(job)` returns `{api_version=5, state=..., ok=..., recovery_required=..., retry_allowed=false}` on a terminal publication result. `LuaRecoveryContract.h` maps the portable seal result into exactly these terminal semantics. The field names are the binding's proposed Lua names; the C++ camel-case members are internal. Nonterminal queued/running states are not publication results. Ordinary transport or staging errors terminate as `not_committed` only when no new record seal was attempted; error codes must be allowlisted, never raw private URL/exception strings.
- `smudge.http.recover_download()` is read-only: it freshly validates both records from reopened storage while holding the exclusive app store lock. It returns `selected`, `empty`, `uncertain`, or `conflict`. Selected responses carry an opaque read handle plus generation as exactly 16 lowercase hexadecimal ASCII characters, never a Lua number (production Lua is int32/float32). Empty has no handle. Uncertain/conflict carry no selected handle and block all new writes. No slot or filesystem path is exposed.
- Proposed handle-based read/seek operations expose payload bytes only (exclude record metadata), reject stale generations/app identities, and revalidate under the same exclusive ownership before reading. These operations and the generation codec are NOT implemented by the envelope mapper.

## Publication semantics

- `committed`: `ok=true`, `recovery_required=false`; storage sync/close plus reopened full record validation selected the exact new generation. Only this state may return a new read handle. This is the observed filesystem acknowledgement contract, not a physical-card power-loss guarantee.
- `not_committed`: `ok=false`, `recovery_required=false`; no new record seal was attempted. Inactive-slot bytes may have changed; this does NOT promise the whole card/filesystem is byte-for-byte unchanged. No automatic retry or new read handle. A later explicit new job still requires fresh full recovery/admission.
- `commit_unknown`: `ok=false`, `recovery_required=true`; a seal/header write may have taken effect despite failed write/sync/close/readback acknowledgement. No retry, erase, rename, rollback, selected handle, or successful cancellation response. Unknown enum values fail closed to this state. The existing validated older slot is not intentionally overwritten.
- Cancellation before first seal mutation may produce `not_committed`; after mutation begins, consume the actual publication outcome, not a cancellation/no-change claim. An acknowledged commit wins over late cancellation. Failed post-mutation acknowledgements remain `commit_unknown` even if a subsequent read seems to select the old record.
- `retry_allowed=false` is intentional in every terminal envelope: retries are never an automatic authority from a response. An explicit new operation is independently admitted after recovery and policy checks.

## Per-app uncertainty ownership and restart admission

Maintain one app-root-owned state `needs_recovery`, `ready`, `busy`, or `uncertain`; no app code or job cancellation can clear it. All initialization/reinitialization starts `needs_recovery`, including app reload and firmware reboot. Before any write, under one exclusive lock, reopen/validate both records, reject I/O uncertainty/conflict/invalid admission or generation exhaustion, and reserve the inactive slot/generation. Preserve the lock through staging, sealing, reopened validation and terminal-state publication. Do not accept a second writer while the previous worker still owns files, even after the UI observes cancellation.

On `commit_unknown`, latch `uncertain` before releasing ownership or exposing the result. Only an explicit fresh recovery performed after the worker and all file handles have drained can clear it to `ready` on selected/empty. An unreadable slot is NOT an absent/corrupt slot; do not fall back around uncertain I/O. Conflict remains blocked without destructive automatic repair. Restart must not bypass this latch: unconditional startup recovery supplies fail-closed admission without claiming an unimplemented durable latch file. The production lock, lifecycle state machine and startup gate are REQUIRED but NOT implemented by this proposal.

Recovery is selection, not retry: a complete newer record can be selected after an earlier unknown outcome. Do not replay the HTTP request. A valid older selected record remains readable under a newly validated handle. No persistent handle survives app replacement/reboot; bind handles to app identity plus store epoch/generation and reject stale completions.

## Compatibility, limits, and remaining gates

The staged Connections client still targets frozen API4 and is NOT API5-compatible until explicitly adapted and tested against these terminal/recovery states. Study scheduling and image decoding are separate incomplete work, not credential blockers. No catalog/API capability advertisement changes are made here.

Executable evidence in this slice covers only C++ terminal-envelope mapping in normal and ASan/UBSan modes. Prior portable and pinned real-FAT synthetic block-device tests cover separate record/staging/sealing behavior. Still required: independent frozen-source review, real Lua bindings with restricted production libraries and numeric configuration, complete uncertainty/startup state machine and lock ownership, bounded generation/handle codec and stale-read tests, Connections adoption, production confined SdFat adapter, target build, and physical SD/network/device acceptance. Host FAT tests do not establish exFAT/SPI/SDMMC or power-loss durability. Target downloads remain disabled.
