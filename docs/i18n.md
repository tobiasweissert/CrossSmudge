# Internationalization

Crosscub keeps user-facing UI text in per-language YAML files and generates the C++ lookup tables used by the firmware.

English is the source of truth. Add new `STR_*` keys to `lib/I18n/translations/english.yaml`, then propagate translations to the other YAML files when possible. If a non-English file is missing a key, the generator falls back to the English text for that language.

## Files

Translation sources live in:

```text
lib/I18n/translations/*.yaml
```

Generated firmware files live in:

```text
lib/I18n/I18nKeys.h
lib/I18n/I18nStrings.h
lib/I18n/I18nStrings.cpp
```

The generator is:

```text
scripts/gen_i18n.py
```

Do not edit the generated files directly. Edit the YAML files and rerun the generator.

## YAML Format

Each language file is a flat `KEY: "value"` mapping.

```yaml
_language_name: "Español"
_language_code: "ES"
_order: "1"
_bcp47: "es"

STR_CROSSPOINT: "Crosscub"
STR_BOOTING: "BOOTING"
STR_BROWSE_FILES: "Dateien durchsuchen"
```

**Metadata keys** (prefixed with `_`):
- `_language_name` — Native display name shown to the user (e.g. "Français")
- `_language_code` — C++ enum name (e.g. "FR"). Please use the [ISO Code](https://en.wikipedia.org/wiki/List_of_ISO_639_language_codes) of the language. Must be a valid C++ identifier.
- `_order` — Historical metadata, still validated for uniqueness but no longer used to compute the `Language` enum order (see `_bcp47` below).
- `_bcp47` — [BCP 47](https://www.rfc-editor.org/rfc/rfc5646) language tag (e.g. `"pt-PT"`, `"ca-valencia"`). Must be unique. Controls the position in the `Language` enum and the visible Settings menu order (English is always first, then the rest sorted alphabetically by this tag). Persisted user language preferences are stored by `_language_code` string, not by the enum ordinal, so changing `_bcp47` (and thus the enum/menu order) does not reset anyone's saved language.

- `_language_name` is the display name shown to users.
- `_language_code` is the generated `Language` enum value and must be a valid C++ identifier.
- `_order` controls enum order. English is always first, and every `_order` value must be unique.

Whitespace inside quotes is significant. Some entries are prefixes joined to a
version, number, or name by their callers. Preserve their leading/trailing spaces
and separators; do not trim every value. Check the assembled result in context.
Standalone headings do not need a trailing separator. When adding a question or
formatted sentence, translate the whole message rather than attaching punctuation
to a translated button label.

---

- Use UTF-8.
- Keep the file as plain `KEY: "value"` lines. Do not add comments.
- Use `STR_*` keys for translatable strings.
- Quote every value.
- Use `\n` for newlines, `\\` for a literal backslash, and `\"` for a quote inside a value.
- Keep UI text concise. Many surfaces are small on the e-ink display.

## Adding Or Changing Strings

1. Add or update the key in `lib/I18n/translations/english.yaml`.
2. Add or update the same key in every non-English YAML file when you have a translation.
3. Regenerate the C++ files:

```bash
python3 scripts/gen_i18n.py lib/I18n/translations lib/I18n
```

4. Build the simulator or firmware to make sure the generated files compile:

```bash
pio run -e simulator
```

For a firmware-target check:

```bash
pio run -e default
```

The generator prints fallback information for missing translations and warns about extra keys that exist outside English.

## Adding A Language

1. Create a new file in `lib/I18n/translations/`, for example `example.yaml`.
2. Add `_language_name`, `_language_code`, and a unique `_order`.
3. Add any translated `STR_*` keys you already have.
4. Run the generator.
5. Build with PlatformIO.

Missing strings will fall back to English, but a new language should not ship with large English-only areas unless that is intentional.

## Generated Runtime Model

`scripts/gen_i18n.py` reads the YAML files and generates:

- `Language`, `StrId`, language-code arrays, display-name arrays, and migration helpers in `I18nKeys.h`
- Flat UTF-8 string blobs and offset tables in `I18nStrings.cpp`
- Character sets for each language, used by font tooling

The flat blob plus offset-table layout keeps lookup simple and avoids a large table of individual C string pointers. When a translation falls back to English, the generated offset uses the English string data instead of duplicating the text.

In firmware code, use `tr(STR_KEY)` for user-facing strings:

```cpp
renderer.drawText(font, x, y, tr(STR_SETTINGS_TITLE));
```

**That's it!** No manual array synchronization needed.

### Adding a New Language

To add support for a new language (e.g., Italian):

#### 1. Create a new YAML file

Create `lib/I18n/translations/italian.yaml`:

```yaml
_language_name: "Italiano"
_language_code: "IT"
_order: "7"
_bcp47: "it"

STR_CROSSPOINT: "CrossPoint"
STR_BOOTING: "AVVIO"
```

You only need to include the strings you have translations for. Missing
keys will fall back to English automatically.

#### 2. Run the generator

```bash
python3 scripts/gen_i18n.py lib/I18n/translations lib/I18n/
```

This automatically updates all necessary code.


### Building With Fewer Languages

Every language is compiled in by default. A fork that only needs some of them can drop the rest at
build time with `custom_i18n_builtin_langs` in `platformio.ini`:

```ini
custom_i18n_builtin_langs = all      ; default: every language
custom_i18n_builtin_langs = de,fr    ; English, German and French only
```

English is always included, since every other language falls back to it. Languages left out
disappear from the language picker and their strings are not compiled in. They keep their enum
value and display name, so code that refers to a language (such as the keyboard layout list)
builds unchanged. A device whose saved language is not in the build shows English, and the saved
setting is left alone, so flashing a build that includes the language brings it back.

The same list can be passed to the generator directly:

```bash
python3 scripts/gen_i18n.py lib/I18n/translations lib/I18n/ --builtin-langs de,fr
```

An unknown code is an error, so a typo cannot silently produce a build without a language.

---

### UTF-8 Encoding

The YAML files use UTF-8 encoding. Special characters are automatically converted to C++ UTF-8 hex sequences by the generator.

### I18N API Reference

```cpp
// === Convenience Macros (Recommended) ===

// tr(id) - Get translated string without StrId:: prefix
const char* text = tr(STR_SETTINGS_TITLE);
renderer.drawText(font, x, y, tr(STR_BROWSE_FILES));
LOG_INF("I18N", "Status: %s", tr(STR_CONNECTED));

// I18N - Shorthand for I18n::getInstance()
I18N.setLanguage(Language::ES);
Language lang = I18N.getLanguage();

// === Full API ===

// Get the singleton instance
I18n& instance = I18n::getInstance();

// Get translated string (two equivalent ways)
const char* text = tr(STR_SETTINGS_TITLE);              // Macro (recommended)
const char* text = I18N.get(StrId::STR_SETTINGS_TITLE);   // Direct call

// Set runtime language
I18N.setLanguage(Language::ES);

// Get current language
Language lang = I18N.getLanguage();

// Persist a user language choice
SETTINGS.language = static_cast<uint8_t>(Language::ES);
SETTINGS.saveToFile();
```

## Persisted Language Setting

The selected language is stored with the rest of the device settings in:

```text
/.crosspoint/crosssmudge-settings.json
```

The `language` field is stored as a stable language code string such as `"EN"`, `"DE"`, or `"HE"`, not as a raw enum number.

Current firmware falls back to `/.crosspoint/settings.json` when the namespaced Crosscub settings file is not present, then saves the loaded settings to `crosssmudge-settings.json`.

Older firmware used:

```text
/.crosspoint/language.bin
```

Crosscub preserves the owner legacy-language migration into `crosssmudge-settings.json`;
retained recovery roots must be inspected on failure. Do not reset language or delete
legacy state merely because upstream stopped reading it. End-to-end legacy/FAT
migration qualification remains pending.

## Validation Checklist

Before submitting translation changes:

1. Run the generator:

```bash
python3 scripts/gen_i18n.py lib/I18n/translations lib/I18n
```

2. Check for accidental fallback English values where a real translation was expected:

```bash
rg -n '^STR_MY_KEY:' lib/I18n/translations
```

3. Build at least the simulator:

```bash
pio run -e simulator
```

4. If the changed text appears in a cramped UI surface, check it on device or in the simulator for clipping.

## Notes For Translators

- Keep translations short where possible.
- Preserve placeholders, punctuation, and units from the English string unless the target language needs different grammar.
- Do not translate internal names that are meant to stay as product or file-system labels.
- If a full translation would be too long for a button hint or compact label, ask for a dedicated short `STR_*` key instead of shortening the full title globally.
